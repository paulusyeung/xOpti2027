# Permissions and security levels (legacy baseline)

Scope: the legacy `Security` matrix, `Staff.SecurityLevel`, the VB procedures that
read them, and the xOpti authorization model they must be reconciled with.

Generated by `scripts/parity/build-permissions.sh` into
`docs/parity/permissions.csv`. Legacy data comes from `$SYNERGY_MDB`, SHA-256
`55088a63b914f745a4bc6803ab07b11576b61e3d7c11e3f3c670bf11c2a5dd2e`; the xOpti
side is parsed from source (`PermissionNames.cs`, `RolesAndIdentity.cs`,
`LegacyUserSeeder.RoleForLevel`), so the comparison cannot drift silently.

Identifiers: `PERM-001` … `PERM-013`.

## Legacy model

`Security` has five rows (`LeveL` 1–5) and eight capability columns. Only one
column is ever read by VB:

| Column | Runtime check | Evidence |
| --- | --- | --- |
| `Cost` | `IsCostOK` | `AppValidation.bas:335-359`, called from `AppUser.bas:16` and at `frmInfoSKU.frm:1770`, `frmInventoryChoice.frm:517`, `frmSpeicalAnalysis.frm:402` |
| `Point_of_Sale`, `Inventory_Control`, `OLAP`, `Information_Centre`, `Coding`, `Report_Centre`, `Preference` | none | no VB source references the column; the menus open unconditionally |

`IsSecurityEnabled` (`AppValidation.bas:187-203`) returns false when `Security`
holds one row; only then do the three cost call sites skip masking. Logon
also does not gate the menus: any `Staff` row that authenticates gets the full
UI (`IsSecurityPassed`, `AppValidation.bas:206-230`).

Staff distribution in the snapshot (61 rows): level 1 = 5, level 2 = 12,
level 3 = 29, level 4 = 13, level 5 = 2. No level 6/7, so the `Security` table
never covers them.

## xOpti model

`PermissionNames` defines 12 permission claims; `RolePermissionMatrix` maps five
roles; `LegacyUserSeeder.RoleForLevel` maps legacy levels to roles
(`>=7 admin`, `>=5 manager`, `>=3 optician`, otherwise `clerk`). Enforcement is
per request via `xopti:permission` claims (`ClaimsCurrentPrincipal.HasPermission`),
with `CostGuard` and `PiiGuard` masking read models.

## Gaps requiring the 3.2 customer decision

These are recorded, not resolved. Do not silently widen or narrow access to make
them match.

1. **Cost visibility is inverted.** Legacy grants `Cost` to level 1 only
   (`Security` row 1; 5 staff). xOpti grants `cost:view` to `manager`
   (level ≥5; 2 staff) and to `admin`, which no legacy level reaches. The
   staff who are allowed to see cost today would lose it, and two level-5
   staff would gain it.
2. **`customer:pii` is unreachable.** It is granted only by `admin`, and
   `RoleForLevel` maps no level 1–5 to `admin`, so zero migrated staff can see
   customer contact details. Legacy allowed all 61.
3. **Reporting narrows from 61 to 2.** `report:financial` is manager-only;
   legacy `Report_Centre` and `OLAP` columns were set for levels 1–5.
4. **Inventory, coding, and preference narrow from 30/17 to 2.** Legacy levels
   1, 2, and 4 held these columns; xOpti grants them to manager only.
5. **`admin` and `purchasing` are unreachable.** `RoleForLevel` cannot produce
   either from the legacy level values, so administrators and purchasers must
   be assigned explicitly before cutover.
6. **Credentials.** Passwords are plaintext and compared directly; they must
   not be migrated. xOpti seeds every staff row with `ResetRequired`. The
   reserved `StaffCode 9999` bootstrap user must not be recreated.

`docs/parity/permissions.csv` carries the per-level breakdown
(`PERM-101`…`PERM-105`) with the exact legacy grants dropped or added by each
role, plus authentication and policy rows `PERM-009`…`PERM-013`.

## Verification

```bash
scripts/parity/build-permissions.sh
```

The script fails if `PermissionNames.cs`, `RolesAndIdentity.cs`, or
`RoleForLevel` change shape, and prints the IDs still marked `gap` (currently
`PERM-002`–`PERM-008`, `PERM-101`–`PERM-105`, `PERM-013`). Task 3.2 closes them
with written customer approval; task 6.4 checks that every `PERM-*` ID is
referenced or explicitly deferred.
