# Spec Delta

## Purpose

Automates repeatable migration of legacy eOptical Access data into PostgreSQL xOpti while preserving traceability and reconciliation evidence.

## ADDED Requirements

### Requirement: Read-only legacy source access
The system SHALL read the configured legacy MDB without modifying it and SHALL fail the run if the source path is missing or unreadable.

#### Scenario: Source is read only
- **WHEN** a migration run starts
- **THEN** the legacy MDB remains unchanged and the run records the source path and row counts

### Requirement: Environment-based configuration
The system SHALL obtain database connections and source paths from environment variables or a local secret store and SHALL NOT require committed credentials.

#### Scenario: Credentials are not committed
- **WHEN** the runner is configured for a target environment
- **THEN** no password or connection secret is written to repository files

### Requirement: Raw staging of legacy data
The system SHALL stage every legacy source table into a PostgreSQL legacy schema while preserving source table names, columns, and values.

#### Scenario: All source tables are staged
- **WHEN** extraction completes
- **THEN** the staging schema contains one table for each legacy source table with matching row counts

### Requirement: Idempotent transformation to target schema
The system SHALL transform staged legacy data into the normalized target schema in a way that can be rerun without creating duplicate target rows.

#### Scenario: Repeated transform is idempotent
- **WHEN** the transform step runs twice against the same staged data
- **THEN** target row counts and aggregate totals remain unchanged after the second run

### Requirement: Legacy identifier preservation
The system SHALL retain legacy identifiers on migrated target records so migrated data remains traceable to its source.

#### Scenario: Migrated records keep source identifiers
- **WHEN** a legacy record is transformed
- **THEN** the target record contains the corresponding legacy identifier values

### Requirement: Data normalization
The system SHALL normalize Access booleans (`-1`/`0`), `REAL` floating-point line numbers via integer rounding, `1900-01-00` date defects (to `1899-12-30`), currency values (`numeric(19,4)`), timestamps (`timestamptz`), text encodings, and Unit Separator (`\x1f`) stream parsing during extraction and transformation.

#### Scenario: Normalized values are valid
- **WHEN** transformation completes
- **THEN** target columns contain PostgreSQL-compatible boolean, numeric, timestamp, and text values with rounded integer row numbers and valid dates

### Requirement: Anomaly detection and reporting
The system SHALL detect known legacy anomalies, including missing transaction headers and orphaned child rows (such as `TxSalePerson` and `TxDetails`), and SHALL route them into quarantine or flagged synthetic stub headers (`is_synthetic = true`) with logged reports instead of violating foreign key constraints or silently copying bad data.

#### Scenario: Missing header is reported
- **WHEN** a transaction detail or salesperson record references a missing transaction header
- **THEN** the run records the anomaly, preserves foreign key integrity via quarantine or synthetic stub, and reports affected identifiers in the exception report

### Requirement: Reconciliation evidence
The system SHALL produce row-count and aggregate reconciliation results covering sales, tax, payments, refunds, inventory quantity and cost by SKU and lot, AR/AP balances, control-number sequences, and order status counts.

#### Scenario: Reconciliation report is generated
- **WHEN** a migration run completes
- **THEN** a pass or fail result with measured differences is available for each reconciliation check

### Requirement: Sequence and control-number advancement
The system SHALL advance target sequences and transaction control numbers (`RC`, `RS`, `SR`, `RJ`, `SJ`, `WC`) to values at least as high as the migrated legacy maximums before cutover by extracting numeric suffixes with regular expressions and synchronizing both PostgreSQL sequences and `Preference`/`TxNextNumber` rows.

#### Scenario: Sequences are safe for new writes
- **WHEN** cutover preparation completes
- **THEN** new transaction numbers generated by the target system cannot collide with migrated legacy numbers

### Requirement: Migration modes
The system SHALL support dry-run, freeze-window sync (fast staging reload + set-based upsert to capture in-place legacy edits), and cutover modes, and SHALL support a read-only comparison mode that writes nothing to either source or target.

#### Scenario: Dry run performs no writes
- **WHEN** dry-run mode is selected
- **THEN** no data is written to the legacy source or target database

#### Scenario: Freeze-window sync captures in-place updates
- **WHEN** freeze-window sync mode is executed
- **THEN** historical transactions and state tables with in-place edits are refreshed without relying on date-range filtering

### Requirement: Master-data-first ordering
The system SHALL migrate master data before opening balances and stock, and historical transactions before enabling normal application writes.

#### Scenario: Ordered migration
- **WHEN** a full migration run executes
- **THEN** dependent records are only transformed after their parent master records exist
